**Internal skill.** It carries this project's specifics and is not for

## Architecture truth — three codebases, read before any claim

`outputs/maracuya/` holds three separate things. Confusing them is the
failure mode this section exists to prevent.

| Directory | What it is | Status |
|---|---|---|
| `app/` | React + TanStack Start + Vite + Tailwind v4 + shadcn/ui | A copy, and its catalogue is stale — see the warning below |
| *(separate repo)* `maracuya-mercado-latino`, branch `main` | The same React app, with the real 172-product catalogue | **This is the web the user looks at. Work here.** |
| `theme/` | Shopify Online Store 2.0 theme, Liquid | Finished and verified; parked, not installed |
| `prototype/` | Vanilla HTML/CSS/JS single page | Historical. The original design study |

**`app/` is where development happens.** It began as a Lovable project the
user preferred over the prototype. Their Lovable access has lapsed, so the
app was made independent of Lovable: its own `vite.config.ts` replaces
`@lovable.dev/vite-tanstack-config`, and nothing under `src/` references
Lovable. Do not reintroduce that dependency, and do not assume the Lovable
MCP server or `lovable.dev` is reachable — the egress proxy blocks both.
**The repo in this container is NOT the web the user sees.** This cost a
session once: `outputs/maracuya/app/src/lib/catalogo.ts` holds 30
hand-written products, 7 categories and 8 countries, while the user's live
web shows **172 products, 10 categories, 15 countries** — and he is right,
not you. The real web is the separate repo
`cristianandrestorogallego-ctrl/maracuya-mercado-latino`, branch `main`,
which is not attached at session start: add it with `add_repo` and clone it
to `/home/user/maracuya-mercado-latino`. It carries
`src/lib/catalogo-productos.ts` (the 172, generated by
`scripts/catalogo-desde-shopify.mjs` from Shopify) plus
`src/lib/lovable-error-reporting.ts`; neither exists in the container copy.
The two agree on `envio.ts` and both have the filter sidebar, so the
catalogue is the whole of the difference.

Before quoting any catalogue figure, or doing catalogue or design work,
settle which copy you are in. Count it, do not recall it:
`grep -c 'nombre:' src/lib/catalogo-productos.ts`. Work the user will see
goes to `maracuya-mercado-latino`.

### You are not the only one writing to that repo

**The user runs a second Claude Code project, called "maracuya", that works
on `maracuya-mercado-latino` too.** He said so on 16 Oct 2026, correcting a
guess of mine that the other writer was a Lovable agent — it is not. The

**That project cannot see this skill.** `maracuya-mercado-latino` has no
`.claude/` directory (verified 16 Oct 2026), so none of this reaches it: not
the brand invariants, not the pending checklist, not the 1-unit stock trap.
Assume the other project is working without any of it, and that it may undo
a decision recorded here without knowing the decision exists. `list_sessions`
does not show that project's sessions from here either.

The git rules below are what keep two writers from destroying each other's
work:

- **Never force-push, rebase, amend or squash anything already pushed**
  there. A merge commit or a fast-forward, nothing else.
- **`git fetch origin main` before starting**, and build on that tip. A
  branch cut from a stale tip is where the conflicts come from.
- **Work on a branch, merge only when the user says so.** `main` is the
  connected branch: pushing to it syncs to the editor and deploys.
- **A non-fast-forward rejection means Lovable pushed while you worked.**
  Merge `origin/main` into your branch, re-run the gates, then push. Do not
  retry the push unchanged and never force it. This has happened twice.
- **Never hand-edit `src/lib/catalogo-productos.ts`.** It is generated by
  `scripts/catalogo-desde-shopify.mjs`; a regeneration discards manual
  edits. Change the script or Shopify, not the file.

### Running that repo here

```bash
cd /home/user/maracuya-mercado-latino
bun install
bun run build && bunx tsc --noEmit && bun run lint   # the three gates
bunx vite dev --host 127.0.0.1 --port 5310           # see below
```

`bun run dev` fails with `EAFNOSUPPORT ::` — it binds IPv6, which this
container has not got. Pass `--host 127.0.0.1` and a port.

The proxy blocks `cdn.shopify.com`, so product photos never load in a local
screenshot. The wells render as flat colour; on the real site the pack
covers most of them. Say so when showing a capture, or the user judges a
design that is not what ships. Google Fonts is blocked too.

**`app/` is not a Shopify theme and cannot be uploaded to Shopify.** It is
React. Selling through it would mean wiring the Shopify Storefront API and
hosting it separately. The user was told this and chose React anyway.
`theme/` is the thing Shopify installs, and it is complete: run
`@shopify/theme-check-node` with `extends: theme-check:all` and it passes
0/0/0.

Never describe any of this as "approved by Shopify" or "Shopify-ready",
and never say the store is live. Nothing is published.

## What is actually in the user's Shopify store

**Everything in that store today is provisional, including what is already
there.** The user said so in as many words: the shop and the draft are
examples; what is real is what gets loaded with them. So treat nothing in
the store as data — not the prices, not the stock figures, not the
metaobjects. Never cite any of it back to the user as a fact about their
business, and never let it reach a customer's screen as though it were.

The pending items, each with the check that settles it, live in
`references/pendientes.md`. **Read that file before saying anything is
done, pending, or fixed** — and before answering "what is left".

Shop `yw4vyu-vf.myshopify.com`, Basic plan, EUR, Spain. Verified by Admin
API on 16 Oct 2026; it is a snapshot, so re-query before repeating it.

- **Name: "MARACUYA mercado latino".** Renamed. The old "Mi tienda" and
  "Tienda Macondo" are both dead; never use either.
- **172 products, all `ACTIVE`** — but every variant sits at **1 unit of
  stock**, `tracksInventory: true`, `inventoryPolicy: DENY`, priced
  **1,99 €** and tagged `precio-provisional`. That single unit is the trap
  documented at the top of `pendientes.md`: a test purchase consumes it and

- **Theme: Horizon, role `MAIN`, and it is the only theme in the store.**
  The MARACUYA Liquid theme is **not** there any more. The zip is still at
  `outputs/maracuya/maracuya-theme.zip` if it is ever wanted back.
- **No custom domain**: `primaryDomain` is still the myshopify host.
- **Headless channel** "Mi Tienda Headless", publication
  `gid://shopify/Publication/374077882702`. A catalogue publication accepts

## Brand invariants — these fire on every visual change

1. **The name carries no accent.** "MARACUYA", never "MARACUYÁ". This was
   changed deliberately across the logo outlines and all copy. The JS
   namespace `window.MARACUYA` was always unaccented and is unrelated.
2. **One palette, two typographies.** Check the files before claiming a
   difference — this entry has been wrong before.

   | | `app/` | `theme/` and `prototype/` |
   |---|---|---|
   | Ground | `oklch(0.982 0.016 88)` cream | `#FFF8EC` cream |
   | Primary | `oklch(0.33 0.107 324)` purple | `#4B204F` purple |
   | Accent | `oklch(0.85 0.145 86)` gold | `#F4C542` gold |
   | Display | Fraunces (Google Fonts) | Georgia |
   | Body | Outfit (Google Fonts) | Arial |
   | Motif | Photography | Drawn passion-fruit seeds and rind arc |

   The colours already agree; only the fonts and the motif differ. The
   app once ran a green primary, which is why `--selva` exists — it now
   holds the same purple as `--primary` and the name is a leftover. Do
   not read the name as a colour. A font or palette change is a brand
   decision: raise it, do not make it.

   **The theme is not behind the app on layout.** `sections/header.liquid`
   already centres the logo with `grid-template-columns:1fr auto 1fr` and
   hangs the menu from a second row, and `sections/hero-offers.liquid` is
   a real carousel whose slides are editable blocks. What the theme does
   not have: the two Google fonts, a "Compra por tradición y país"
   section, and anything about recipes.
3. **The logo SVGs are traced outlines from the official kit** — in
   `prototype/brand/`, `theme/assets/` and `app/src/assets/`. Edit them
   only by removing or moving existing path data. Never redraw a glyph,
   never substitute a font-rendered wordmark.
4. **Never invent commercial substance.** No reviews, ratings, certifications,
   real brand names, stock figures, delivery guarantees or health claims.
   Product brands in the catalogue are fictional on purpose, to avoid
   trademark and impersonation risk — keep them fictional even when copying
   the layout of a reference site that uses real ones. Unknown product data
   uses the `PENDING` sentinel and renders as "pendiente de confirmar".
   **Allergens are the sharp edge of this rule.** "Sin gluten" is a legal
   claim, not copy. Nothing on the site may state what a product contains
   or is free of until a supplier's sheet says so; the standing wording is
   that it is pending and the label on the package decides.
5. **Everything on the site is a demonstration** and says so. The demo
   notices in the header strip and footer are load-bearing, not decoration.
6. **No third party serves part of the shop.** Flags are eight local SVGs
   in `app/src/assets/banderas/`, mapped by `banderaUrl` in `catalogo.ts`;
   they used to come from flagcdn.com and must not go back. Google Fonts
   is the one exception already in place — it is blocked by the egress
   proxy here, so a `fonts.googleapis.com` failure in a Playwright run is
   the sandbox, not a bug.

## The verification loop — do not skip, do not extend

Work in bounded passes: build the whole change, inspect once in a batched
round covering desktop and mobile together, fix everything that round shows
in one batch, confirm with at most one more round, then stop.

In `app/` the gates are the project's own, and all three must pass before
a change is done:

```bash
cd outputs/maracuya/app
bun run build        # compiles, and regenerates src/routeTree.gen.ts
bunx tsc --noEmit    # tsconfig is strict; this catches what the build does not
bun run lint         # prettier is enforced; `bun run format` fixes it
```

`react-refresh/only-export-components` warnings are inherent to shadcn's
pattern — they are expected, and are not errors. Chromium for screenshots
is at `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`; pass
`executablePath` and `args: ['--no-proxy-server']` or Playwright tries to
download a build it cannot reach. Google Fonts is blocked by the proxy, so
Fraunces and Outfit fall back to their local stacks in screenshots taken
here — that is the environment, not a bug.

Before calling any visual change done:

1. Screenshot desktop (1280) and mobile (390) in the same run.
2. Confirm zero `pageerror` and zero console errors.
3. Confirm no horizontal scroll at 390px.
4. Run the functional regression (menu focus handling, recipe package
   maths, cart, variants, filters) — a visual change that breaks the
   package calculator is a failed change.
5. Check that new colour pairs meet WCAG AA, **in both themes**. The
   recurring bug in this project is hardcoded cream text on `var(--primary)`:
   it passes in light mode and drops to about 3:1 in dark mode, where
   `--primary` becomes a light purple. Use `--on-primary-soft`, never a
   literal `rgba(255,248,236,…)`, on any surface painted with `--primary`.
   This check catches it:

   ```bash
   grep -n 'rgba(255,248,236,' outputs/maracuya/prototype/styles.css \
                               outputs/maracuya/theme/assets/maracuya.css
   ```

   This trap is specific to the purple codebases. `app/` states every
   colour as an oklch token pair in `src/styles.css`; check those instead.

   Every hit must sit on a hardcoded dark ground (the hero scrim, a
   `rgba(0,0,0,…)` overlay), not on `var(--primary)`.
